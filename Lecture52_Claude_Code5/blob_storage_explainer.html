Auto Data Analyst Agent · Lecture 52

Why the file goes to blob storage next

The upload screen already lets someone pick a CSV or XLSX and checks it. But the file never leaves their browser. Before an AI agent can analyse it, the file needs a safe, permanent home. That home is blob storage.

Where we are

The app has a gap in the middle

Steps 1 and 2 are built. Steps 4 and 5 are the exciting part, the agent and its insights. But step 4 cannot start, because there is no place the agent can get the file from.

The problem

Right now the file only lives in one browser tab

In the code, the selected file is just a variable in React state (useFileUpload.js). That causes four problems as soon as we add the agent:

It vanishes on refresh

Close the tab or press F5 and the file is gone. The user has to upload again.

The agent can't reach it

The analysis runs on a server. A server cannot read a file sitting in someone's browser.

Analysis is slow

Profiling 5,000 UPI rows and calling an LLM can take a minute. We can't keep a web request open that long. The job needs to pick up the file later.

We need it again and again

Quality checks, charts, then follow-up questions in plain English. Each step re-reads the same file.

The concept

What is blob storage?

Blob stands for Binary Large OBject. It just means “a file, treated as a bag of bytes.” Storage doesn't care whether it's a CSV, a photo or a video.

Blob storage is a cloud service that keeps huge numbers of files safely and cheaply. Your code talks to it over the internet: put this file, get that file, delete this file.

Analogy: Google Drive for your app, without the screens

Google Drive is file storage built for people, with folders and a nice UI. Blob storage is file storage built for programs. There's no UI to click through, only an API. Your app is the only “person” using it.

Notice the file is saved under an ID we generate (7f3a91c2), not under the user's filename. Two people uploading data.csv must never overwrite each other.

Storage account
Your space in the cloud provider. Holds everything.
Container / bucket
A top-level folder, like uploads. Azure calls it a container, AWS calls it a bucket.
Blob / object
One file. Can be a few bytes or many gigabytes.
Key
The blob's full name, e.g. uploads/7f3a91c2/original.csv. The slashes only look like folders.
Signed URL
A temporary link that lets someone upload or download one blob without a password. Covered below.
Azure Blob Storage AWS S3 Google Cloud Storage Cloudflare R2 Azurite (local, free) MinIO (local, free)

They all work the same way. Learn one and the others are easy.

The usual pattern: files go in blob storage, facts about the files go in a database (who uploaded it, when, status, where the blob is).

How to upload

Don't push 100 MB through your own server

The obvious approach is: browser sends the file to our API, and our API forwards it to blob storage. It works for small files, but the 100 MB passes through our server twice.

The better approach: our server only hands out a permission slip, called a signed URL. The browser then uploads the file directly to blob storage.

Analogy: the cloakroom ticket

You don't hand your suitcase to the hotel manager. The manager gives you a ticket for locker 42, valid for 10 minutes. You walk to the locker yourself. The signed URL is that ticket. It works for one file, one action (upload) and a short time, and then expires.

What this unlocks

Once the file has a home, the agent can start

Background analysis

A worker reads uploads/{id}/original.csv whenever it's ready. The user isn't stuck on a loading spinner.

Re-run and ask questions

Every Q&A question reads the same stored file. No re-uploading.

Save outputs

Charts and reports from the agent go into reports/{id}/ in the same storage.

Clean up automatically

Storage can delete old uploads after 7 days. Good for privacy and cost.

For the instructor

How to teach this in class

  1. Start with the demo. Upload upi_transactions.csv, then refresh the page. The file is gone. Ask: “How would the agent read this?”
  2. Show the gap diagram. Steps 1 and 2 are done, step 4 needs the file, so step 3 is next.
  3. Explain blob with the Google Drive analogy, then the account → container → blob picture.
  4. Walk the comparison table. Let students guess each answer before you reveal it.
  5. Draw option A on the board first. Ask what goes wrong with 50 users uploading 100 MB at once. Then show option B and the cloakroom ticket.
  6. Build it live: one backend route that returns a signed URL, then the PUT with a progress bar. Use Azurite or MinIO so nobody needs a cloud account.

Quick check for students

What does “blob” stand for, and why doesn't storage care about the file type?

Binary Large OBject. Storage only sees bytes. Opening the file as a CSV or XLSX is our code's job.

Why not save uploads to the server's own disk?

That disk disappears when the server restarts, and with two or more servers the file is only on one of them.

Why do we save the file as uploads/{id}/original.csv instead of the user's filename?

Filenames clash (everyone has a data.csv) and can contain unsafe characters. A generated ID is unique and safe.

What would happen if a signed URL never expired?

Anyone who got hold of the link could keep uploading or overwriting files forever. Short expiry limits the damage.

The browser already checks file size. Why does the backend check again?

Browser code can be changed or skipped by the user. Only checks on the server can be trusted.
